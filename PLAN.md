# B-extension: git-aware tree-sitter-bash (single merged grammar)

## Goal

Extend tree-sitter-bash so that `git` invocations parse as first-class nodes
in the *same* parse tree as the rest of the script — no language injection,
no second parser, no second tree. This is for static analysis / git command
extraction: replacing the hand-rolled node-walking logic in
`kilo-code-git-canonical/git-normalizer/src/normalize.ts` with real parse-tree
structure, and making that structure available to other future consumers
beyond `normalize.ts`.

This branch supersedes the approach on `A-injection` (`demo/git-cmd-grammar-v2`
and `demo/git-cmd-grammar-v3`), which built a fuller per-subcommand generated
grammar wired in via an injection query
(`demo/git-cmd-grammar-v3/integration/bash-injections.scm`). That approach is
explicitly not the direction here — see "Rejected approaches" below.

## Grammar design

**A classified `git_command`, not a flat one.** The parse tree must *know*
which tokens are global options, which token is the subcommand, and which
tokens are the subcommand's own options — not emit an undifferentiated flat
stream that a consumer has to reinterpret. The one fact that must be 100%
certain is the subcommand: if the grammar cannot establish it, it does not
produce a `git_command` at all, and the invocation falls through to a generic
`command`, exactly as today.

To make the subcommand certain, the grammar carries two small, **generated**
tables (from git's own docs via the existing extraction pipeline — not
hand-written):

1. **Global option table** — every known global option plus its *structural*
   arity (does it consume the following token, or is it self-contained?).
   This is what defines where the subcommand starts: `git -C dir commit`
   requires knowing `-C` consumes `dir`. Without it the boundary is
   ambiguous and unsolvable post-parse — `git -C commit push` (a directory
   literally named `commit`) would otherwise claim `subcommand=commit`,
   which is wrong.
2. **Subcommand name list** — the set of valid subcommands (from
   `command-list.txt`). A candidate subcommand is accepted only if it is in
   this list; anything else fails closed to a generic `command`.

Both tables are bounded and static: ~30 global flags + ~190 subcommand names
is one flat choice in the grammar — a few KB, negligible parser/storage cost.
They are regenerated by the same pipeline on the same pinned `GIT_REF` bump
as `git-data/*.json`.

**Subcommand options stay arity-agnostic.** The grammar does NOT encode which
subcommand flags take values (`git commit -m` vs `git commit -v`). Nothing in
the tree structure depends on that knowledge — the subcommand boundary is
already fixed. Arity/retention/meaning of subcommand options lives entirely in
`git-normalizer/src/git-data/*.json` (generated from git's docs by
`demo/git-cmd-grammar-v3/pipeline/extract_options.py`) and is applied *after*
parsing, in `option-data.ts` / `normalize.ts`. This is the line that separates
this design from the rejected `A-injection` approach: that one baked
per-subcommand option *arity* into generated grammar rules (semantic knowledge
no parse tree needs), which is what made it huge.

**Flat token stream within each group, with one lexical exception.** Under
`git_command`, flags and words are flat siblings within their group (global
vs subcommand) — no heuristic pairing of a flag with the token that follows
it (`git commit -m foo bar` does not nest `foo` under `-m`). Heuristic pairing
would frequently be wrong (any boolean flag followed by a positional) while
looking authoritative, which is worse than leaving pairing to the consumer
that actually has the arity data.

The one exception: `--opt=value` *is* split into a structured `git_flag`
node with `name`/`value` fields, because the `=` delimiter for long options
is lexically unambiguous — it needs no arity knowledge, unlike space-
separated `-m value`. This applies to both global and subcommand options.
Leaving this flat would be inconsistent with the principle above, not
simpler.

**Trigger condition for `git_command`.** Fires only when all of the
following are statically certain:
- the command name is provably `git` — a bare literal word `git`, or a
  path-like word whose basename — after stripping any `/`, `\`, leading
  `\\` or `//`, and a case-insensitive `.exe` suffix — is exactly `git`
  (mirrors `binaryName()` in `normalize.ts:282`);
- every global option before the subcommand is a known global option (from
  the baked-in table), so its arity is known and no option value is mistaken
  for the subcommand;
- a token in the subcommand position exists and is a valid subcommand name
  (from the baked-in list).

Everything else stays a generic `command` node, exactly as today:
- quoted strings (`"git"`), concatenations (`gi""t`), command substitutions
  (`$(echo git)`) — these need semantic resolution the grammar can't do;
- wrapped invocations (`sudo git commit`, `env git push`,
  `bash -c "git push"`) — wrapper-peeling and script recursion stay in
  `normalize.ts` (`WRAPPERS`, `findScript`), unchanged;
- `git` with global options but no subcommand (`git`, `git --version`,
  `git -h`) — a `git_command` with `global_option` nodes and no `subcommand`
  field, since these are valid git invocations even though no subcommand
  follows;
- unknown globals or an unknown subcommand (`git frobnicate`) — fail closed
  to a generic `command`.

## Node shape (sketch)

```
git_command
  name: (word)                          ; the "git" / path-to-git token itself
  global_option: (git_flag | git_word)* ; global opts + their values, before the subcommand
  subcommand: (git_word)                ; certain — validated against the subcommand list
  option: (git_flag | git_word)*        ; subcommand opts, flat, in source order
    ; git_flag for "--opt=value":
    git_flag
      name: (git_flag_name)             ; "--opt"
      value: (git_flag_value)           ; "value"
    ; git_flag for anything else ("-m", "--verbose", "-mFoo", "--opt"):
    git_flag                            ; opaque text, no fields
```

Exact rule/field names to be finalized during implementation to match
tree-sitter-bash's existing naming conventions (`command_name`, `_literal`,
etc.) — not a decision that needs sign-off, just consistency with the
surrounding grammar.

## Scope of this branch

Includes rewiring `normalize.ts`:
- `canonicalizeCommandNode` / `canonicalizeGit` walk `git_command`,
  `global_option`, `subcommand`, and `option` nodes directly. Because the
  grammar already validates the subcommand, `normalize.ts` no longer guesses
  it; unknown-subcommand / unknown-global shapes never arrive as
  `git_command` (they stay generic `command` and pass through).
- The generic `command` path (wrapper peeling, script recursion, dynamic
  command names) is unchanged and still handles everything the grammar
  doesn't claim.
- `tree.rootNode.descendantsOfType(...)` calls need to look for both
  `command` and `git_command`.

This proves the grammar end-to-end against Kilo's actual use case rather
than shipping an untested grammar nothing consumes.

## Distribution

Internal fork only. No npm/crates.io publish. `git-normalizer` consumes it
via a local/relative dependency, with its own compiled wasm build replacing
the stock `tree-sitter-bash/tree-sitter-bash.wasm` import
(`normalize.ts:48`).

## Upstream sync

`origin` (`kristianrusnak/tree-sitter-bash`) is itself a fork; `master` here
tracks tree-sitter-bash upstream. Git-specific additions to `grammar.js`
are kept isolated as an overlay (additions/overrides, not scattered edits to
existing bash rules) — mirroring how tree-sitter-typescript composes off
tree-sitter-javascript's rules object — so upstream bash fixes can be merged
in later and `tree-sitter generate` re-run without fighting hand-merged
diffs.

## Rejected approaches (and why)

- **Injection** (`A-injection`, `bash-injections.scm`): produces two parse
  trees glued by ranges, not one merged tree. Explicitly ruled out from the
  start of this design.
- **Per-subcommand option grammar** (`demo/git-cmd-grammar-v3/grammar`,
  data-driven `grammar.js` codegen from `git-data/*.json` baking in arity
  per subcommand): more upfront machinery (a full codegen + regeneration
  pipeline keyed to subcommand data) for something a post-parse data layer
  already does correctly. Superseded by the design above, which keeps
  subcommand-option arity out of the grammar. Note the distinction: the
  bounded global-option table baked into this design is *structural* (it
  defines the subcommand boundary); v3's per-subcommand rules were
  *semantic* (option arity/meaning no tree structure depends on).

## Cleanup

`demo/git-cmd-grammar-v2` and `demo/git-cmd-grammar-v3`'s generated-grammar
and injection-query pieces are archived/retired on this branch (they exist
on `A-injection` for reference). Only the extraction pipeline
(`pipeline/extract_options.py` → `git-data/*.json`) is carried forward,
since `normalize.ts`/`option-data.ts` already depends on its output
independent of how the grammar itself is built. The pipeline is extended to
also emit the global-option table and the subcommand-name list for the
grammar overlay.
