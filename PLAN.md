# A-injection: git-aware grammar via injection, for `normalize.ts`

Generated by Claude Code (Sonnet 5) — design settled via an interactive
grilling session with the user, 2026-09-03. Captures the decisions reached,
not just a proposal.

## Goal

Give `kilo-code-git-canonical/git-normalizer/src/normalize.ts` a real
git-command grammar to resolve `git commit` / `git push` structure, and give
a broader set of git subcommands enough grammar depth to support a new,
separate, exploratory detection feature (structural pattern-matching over
parsed git commands, e.g. "`commit` used with `--amend` and `-a`").

This builds on the existing prototype already on this branch
(`demo/git-cmd-grammar-v2`, `demo/git-cmd-grammar-v3`) rather than replacing
it with the single-merged-grammar approach explored on `B-extension`. See
"Relationship to B-extension" below — the two branches now represent a real
fork in direction and both are live.

## Architecture: injection, not a fork of tree-sitter-bash

`tree-sitter-bash` itself stays completely unmodified. A git command's text
gets a **second, separate parse** with a standalone git grammar (the
approach `demo/git-cmd-grammar-v3`'s README already argues for and builds:
one `parse()` call for bash, a second for git, never merged into one tree).

**Difference from the v3 prototype as built:** v3's injection layer
(`integration/bash-injections.scm`) exists to *find* git commands inside an
arbitrary bash script for a generic host (an editor). `normalize.ts` doesn't
need that — Kilo already hands it exactly one pre-identified `command` node
per call (verified in `kilo-normalizecommand-contract.md` on the
`kilo-code-git-canonical` side). So the integration into `normalize.ts`
skips the query-based "find" step entirely and goes straight from "this
command's binary resolves to `git`" (already determined by the existing
`binaryName()` walk) to "re-parse its text with the git grammar." The
query-based injection layer stays in `tree-sitter-bash/demo` for its
original purpose (editor tooling via `bash-injections.scm`), unchanged.

## Scope split: canonicalize() vs. detection

Two consumers, deliberately different depth requirements:

1. **`canonicalize()`'s canonical-string output** — stays scoped to exactly
   `git commit` and `git push`, matching the governing spec
   (`git-command-canonicalization.md`'s 29-row table, which covers only
   these two subcommands). Its `canonicalizeGit()` internals get rebuilt to
   read the git grammar's typed nodes (`subcommand`, `global_option`,
   `subcommand_option` fields) instead of the current hand-rolled
   `tokenize()`/`resolve()` string walk. No other part of `normalize.ts`
   changes: wrapper-peeling (`WRAPPERS`), shell-script recursion
   (`findScript`, `bash -c "…"`), and the passthrough rule are bash-level
   concerns, not git-grammar concerns, and stay as they are unless the
   grammar swap forces a specific touch (none identified so far). No spec
   doc changes — behavior for commit/push does not change beyond what a
   correct grammar-driven implementation should already produce.

2. **Detection (new, exploratory)** — a broader, deeper set of subcommands
   get real per-command grammar data, purely to prove structural
   pattern-matching works beyond commit (the way v3's `demo/scan.js`
   already demonstrates for `commit-no-verify`, `commit-amend-with-all`,
   `commit-no-gpg-sign`). No defined export or Kilo-facing API yet — this
   is a proof, not a shipped feature.

## Subcommand coverage

- `commit`, `push`: full depth, feed both canonicalize() and detection.
- Starting default for the broader detection-only set: `checkout`, `reset`,
  `branch`, `merge`, `rebase`, `clone`, `fetch`, `pull` — commands that can
  rewrite history, change remotes, or discard work, which is where
  permission/deny-rule detection is most valuable. Not locked: each
  addition is mechanically independent (one `fetch_source.py` +
  `extract_options.py` run against git's docs, one new `data/<cmd>.json`,
  one new `choice()` arm in `grammar.js`), so this list can grow
  incrementally without revisiting the architecture.
- Subcommands outside this set: no grammar-level recognition; `normalize.ts`
  keeps falling back to its existing generic/`EMPTY` handling exactly as
  today.

## Cost accepted

A second compiled grammar (its own wasm) alongside `tree-sitter-bash`'s, and
every git command's text parsed twice (once by bash, once by the git
grammar). Accepted as fine for this work — exploratory, correctness over
footprint. This does reopen the constraint noted below.

## Known open tension — not resolved here

The prior `kilo-code-git-canonical` implementation task
(`implementation-plan-canonicalize.md`) stated for its own scope: no new
dependencies, `web-tree-sitter`/`tree-sitter-bash` versions pinned to match
Kilo's shipping checkout. Adding a second compiled grammar as a dependency
of `git-normalizer` sits in real tension with that. Left explicitly open —
flagged, not decided — until this work is ready to move toward actually
shipping in `canonicalize()`.

## Relationship to B-extension

`B-extension` (already on this repo, see its own `PLAN.md`) independently
designed the opposite bet: a single merged grammar forked into
`tree-sitter-bash` itself, arity-agnostic (flags stay flat, no per-subcommand
generated rules), explicitly rejecting both injection and the per-subcommand
generated-grammar approach this plan builds on. That branch's rationale is
real and worth reading before either branch goes further — in particular its
argument that baking arity into the grammar (which detection coverage here
requires, subcommand by subcommand) duplicates what `option-data.ts`
already resolves correctly post-parse. This plan proceeds on `A-injection`
per the user's explicit direction; the two branches are not yet reconciled,
and that reconciliation is itself an open question, not an oversight.

## Not decided here (deferred, not silently assumed)

- Exact list of subcommands beyond the starting default.
- Detection feature's eventual API/export shape, if it graduates from
  exploratory.
- How (or whether) to reconcile with `B-extension`.
- How the pinned-dependency constraint gets satisfied before shipping.
